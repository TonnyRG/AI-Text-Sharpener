## 1. 背景与目标

### 1.1 问题
当前主流 AI 生图模型（GPT-5.5、Nano Banana、Imagen 3、Flux 等）已能稳定生成包含正确中英文、数字、符号的图片，零乱码率接近商用水准。但 AI 生成的图片中，**文字部分的渲染锐度始终低于原生矢量文字**——字符边缘存在抗锯齿"果冻感"，放大后模糊，在 PPT、海报、宣传图等需要高质量呈现的场景下表现不佳。

现有的"文字锐化"工具（Pokecut、LetsEnhance、PicWish 等）走的是**超分辨率/像素增强**路线，只能改善已有像素，无法达到真正的矢量级锐度。

### 1.2 目标
开发一个工具，将 AI 生成图片中的文字部分**识别 → 软擦除 → 用矢量文字（SVG）叠加替换**，使最终图片中的文字达到与原生 PPT/矢量软件相同的锐度，同时保持原图的设计语境（位置、字号、颜色、字体感觉）不变。

### 1.3 核心使用场景
本项目的直接驱动场景是**学术答辩 PPT**：用户使用 GPT-5.5 生成整套 PPT 图片（如 Shiny-PreADME 答辩 PPT），需要将这些图片转换为文字锐利的版本，保留原 AI 设计风格的同时获得专业级文字呈现。

## 3. 核心设计原则

### 3.1 叠加而非擦除（Overlay, not Erase）
传统思路是用神经 inpainting 擦除原文字 → 在空白处写新文字。本项目反其道而行：
- 在原模糊文字**正上方**叠加锐利 SVG 文字
- 原文字成为"防锯齿垫底"，新文字遮挡得严严实实
- 仅在边缘做轻量"软擦除"消除光晕外溢

**优势**：避开神经 inpainting 的不稳定性、成本和延迟；保留原图的所有视觉细节。

### 3.2 用户预先指定字体（Font Pre-specification）
"识别原图字体并匹配"是物理上限——AI 生成的字体不在任何字体库中。本项目假设用户在生图阶段已经指定了字体（如"使用微软雅黑"），工具直接用真实字体渲染。
- 输入：图片 + 字体清单（标题/正文/强调，可多组）
- 工具按检测到的文字大小自动归类（大字号 → 标题字体）
- UI 支持逐区域覆盖默认归类

### 3.3 区域级选择性替换（Per-region Opt-out）
图表内的文字（boxplot 轴标签、图例）替换风险高、收益低，应让用户**保留这些区域为原图**。工具在 UI 上让用户勾选哪些区域要替换。

### 3.4 本地优先 + 可选云端兜底
默认使用本地 PaddleOCR 处理；置信度低或失败的区域可选回退到 Vision LLM（GPT-4V/Claude Vision/Gemini）由用户配置自己的 API Key。**不强制依赖任何云端服务**。

### 4.2 各模块详解

#### 模块 ① 文字检测
- **主引擎**：PaddleOCR PP-OCRv4 (DBNet 检测头)
- **输出**：每个文字区域的多边形 bbox（支持倾斜/弯曲）
- **后处理**：
  - 合并垂直距离 < 5px 的相邻 bbox（同一段落）
  - 过滤面积 < 20px² 的噪声 bbox

#### 模块 ② OCR 识别 + 样式分析
- **文本识别**：PaddleOCR 多语言模型（中英日韩 + 80 种小语种）
- **置信度**：< 0.7 触发 Vision LLM 兜底（可配置）
- **样式提取**（每个文字区域）：
  - **颜色**：在 bbox 内做笔画骨架（skeleton）提取 → 取骨架像素中位 RGB（避开抗锯齿边缘）
  - **字号**：bbox 高度 × 0.85（经验值）
  - **粗细**：笔画宽度 / 字高比例 > 0.12 判为 Bold
  - **倾斜**：字符斜率分析（OCR 引擎附带）
  - **背景色**：bbox 外侧 2~3 像素环带的中位 RGB

#### 模块 ③ 软擦除
不调用神经 inpainting，使用经典图像处理：
1. 在 bbox 内填充模块 ② 采样的背景色
2. 边缘做 3~5 像素羽化（Gaussian blur + alpha mask）与原图融合
3. 若背景是渐变/纹理，使用更小的羽化半径减少色块感

**关键洞察**：擦除质量不需要完美，因为上面会盖一层锐利文字。只要解决光晕外溢即可。

#### 模块 ④ SVG 文本叠加
- 每个文字区域生成一个 `<text>` SVG 元素
- 属性映射：
  - `x, y`：bbox 中心对齐
  - `font-family`：模块 ① 用户指定 + 按字号归类的字体
  - `font-size`：模块 ② 推断字号
  - `fill`：模块 ② 推断颜色
  - `font-weight`：模块 ② 推断粗细
- 输出形式：
  - **可编辑层**：原图 (PNG) 作为 `<image>` 背景 + 叠加 `<text>` 元素
  - **扁平化**：渲染为 PNG（用 resvg 或 librsvg）

#### 模块 ⑤ 用户校对 UI
Web 应用（FastAPI + 前端 Canvas），核心交互：
1. **左侧画布**：显示原图 + 半透明覆盖的文字 bbox（按状态着色）
   - 蓝色：默认替换
   - 灰色：用户取消（保留原图）
   - 红色：OCR 低置信度（需人工校对）
2. **右侧面板**：选中区域显示
   - OCR 识别的文字（可编辑）
   - 字体下拉（从用户预指定的清单选）
   - 字号微调
   - 颜色拾取器
   - 位置 X/Y 微调
3. **顶部工具栏**：批量操作（全选/反选/按字号过滤）
4. **底部按钮**：导出 PNG / SVG

## 5. 技术栈

| 层次 | 技术 | 理由 |
|---|---|---|
| 后端语言 | Python 3.11+ | OCR/图像处理生态最完整 |
| OCR 引擎 | PaddleOCR 2.7+ | 中英文 SOTA，开源，本地运行 |
| 图像处理 | Pillow + OpenCV | 软擦除、颜色采样、bbox 操作 |
| SVG 渲染 | resvg-py | Rust 实现的高质量 SVG → PNG |
| Web 框架 | FastAPI | 轻量、类型安全、自带 OpenAPI |
| 前端 | Vanilla JS + Konva.js | Canvas 操作库，比 Fabric.js 更轻量 |
| 打包 | Docker + PyInstaller | 一键部署 / 桌面分发 |
| 可选云端 | OpenAI / Anthropic / Google SDK | 用户自配 API Key |

**所有依赖均为开源 + 宽松许可（Apache 2.0 / MIT / BSD）**，便于 GitHub 发布。

## 6. MVP 范围

### 6.1 MVP 包含（v0.1，预计 2~3 周）
- ✅ 单张图片处理（不支持批量）
- ✅ PaddleOCR 中英文检测识别
- ✅ 软擦除 + SVG 叠加
- ✅ 用户预指定 1~3 个字体
- ✅ Web UI 校对（基础版）
- ✅ 导出 PNG 和 SVG
- ✅ Docker 部署

### 6.2 MVP 暂不包含（推到 v1+）
- ❌ 批量图片处理
- ❌ Vision LLM 云端兜底
- ❌ PPTX 输出
- ❌ 阴影/描边等特效复刻
- ❌ 图标内文字的智能识别（区分"文字"vs"图标元素"）
- ❌ 字距/对齐自动优化
- ❌ 桌面应用打包

### 6.3 验收标准（针对 Shiny-PreADME 答辩 PPT 15 张图）
- **OCR 准确率** ≥ 95%（中英文）
- **位置偏差** ≤ 3 像素（人眼不可察觉）
- **处理时间** ≤ 30 秒/张（本地 GPU）
- **用户校对时间** ≤ 5 分钟/张
- **观感**：盲测中 ≥ 80% 的人认为锐化后版本明显优于原图

## 8. 已知限制

1. **复杂特效文字无法 100% 还原**：渐变填充、3D 浮雕、复杂光效等需要专门检测算法，MVP 不支持
2. **图标内文字误判风险**：圆形数字标号、icon badge 内的数字可能被识别为可替换文字——需要用户手动取消
3. **嵌入图表的文字处理**：boxplot 轴标签等是图表的一部分，理论上不应替换，但 OCR 不区分——通过 UI 让用户选择保留
4. **极端艺术字识别率低**：高度变形的标题字（如波浪、扭曲、镂空）OCR 可能失败，回退到人工输入
5. **字体许可问题**：用户必须自行确保使用的字体（如微软雅黑）在其使用场景下有合法许可，工具本身不分发字体
